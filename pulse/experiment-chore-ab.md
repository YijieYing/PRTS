# 实验：让 agent 接管杂务，用户的体感会怎样（设计稿 v0.1，2026-11-12）

用户提出：在 EchoAsRecord 里实施「杂务交给 agent」的规则，NatureCalls 不实施，比较两边的体感。
输入、输出、杂务的定义见 [README.md](README.md) §一。

## 问题
用户不确定：agent 接管杂务以后，会不会在用户看不见的地方积累问题，比如架构走样、重复实现、接口不一致。
用户的判断：靠两样东西兜底。
1. **加强自检**：agent 定期自查，不靠用户盯。例子：11-10 半夜，用户让「Ear 项目架构」session 检查仓库里有没有重复实现、有没有不符合接口的地方，确实查出了问题。
2. **保留最小的架构思考**：项目开始时由用户敲定文件结构和 glossary，之后 agent 只能在这个框架里动。

这两样就位以后，再尽量减少用户花在杂务上的时间。

## 两组
| | EchoAsRecord（实施） | NatureCalls（对照） |
|---|---|---|
| 架构底线 | 文件结构和 `docs/glossary.md` 由用户定；改动它们要问用户 | 照旧 |
| 自检 | agent 定期自查（见下），只把需要用户决定的结论交给用户 | 照旧，用户想到时再查 |
| 杂务 | 按 `~/PRTS/AGENTS.md` 第一条：agent 自己做完；能自己定的写明理由自己定；必须问的攒成一批；汇报只给结论 | 照旧 |

### 自检的内容（实施组）
- 有没有重复实现：同一件事在两个地方各写一遍。
- 有没有不符合接口：实现和 `contracts/`、模块文档对不上。
- 有没有偏离 glossary：新出现的名字没登记，或者同一个概念有两个名字。
- 文件结构有没有走样。
- 什么时候查：每次合并进 `dev` 之后，外加每周一次全量自查。由 agent 自己触发，不等用户提醒。
- 结果：小问题 agent 直接修，并在汇报里列出来；需要用户决定的（比如改接口、改 glossary）进 question queue。

### 规则放在哪
EchoAsRecord 是和安阳等人共用的仓库，这些规则只约束用户自己的 agent，所以不能提交进仓库，否则会影响合作者的 agent。
- 规则写在仓库根目录的 `CLAUDE.local.md`。Claude Code 会自动读取它。
- 把它加进 `.git/info/exclude`，和现有的 `local-notes/` 一样不进 git。
- 派给 Codex 的任务说明里附上同样的规则。

## 测量
1. **pulse 每日回顾**，按项目分开统计：
   - 杂务时间、输入和输出时间；
   - 用户发出的消息里，有多少是杂务性的（确认、催促、解释过程细节）。
2. **体感**：每天回顾末尾问一个问题，「今天在这个项目上，你觉得被杂务打扰的程度」，1–5 分，另附一句话。
3. **质量护栏**，确认省下来的时间不是靠牺牲质量换来的：
   - 自检发现的问题数；
   - 返工次数；
   - CI 失败次数；
   - 合作者反馈的问题。
4. **用户被迫介入的次数**：agent 本该自己处理、结果还是拉了用户进来的情况。

## 效度威胁
- **两个项目本来就不同**：EchoAsRecord 是带合作者的研究工程，NatureCalls 是有截止日期的课程游戏，杂务的多少本身就不一样。
  - 应对：用「每合并一个 PR 用户花了多少杂务时间」这类相对指标，并记下截止日期等特殊情况。
  - 可选：一周后对调（交叉设计），用来排除项目差异。
- **用户知道自己在哪一组**，没法盲测：体感分会受期待影响。应对：以 pulse 的客观时间为主，体感为辅。
- **工作量每天不同**：应对是看两周以上的趋势，不看单日。

## 前提和启动顺序
1. pulse 每日回顾 v1 能按项目统计（ROADMAP R2 第 1 步）。没有它就没有客观数据。
2. EchoAsRecord 的架构底线确认：现有的文件结构和 `docs/glossary.md` 是否就是用户认可的版本。
3. 在 EchoAsRecord 写好 `CLAUDE.local.md`，并通知正在做 Ear 的各个 session。
4. 开始计时，至少两周。
