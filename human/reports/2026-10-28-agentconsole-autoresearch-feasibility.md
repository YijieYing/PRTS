# AgentConsole 升级 × 果蝇 autoresearch：可行性评估

2026-10-28，总控 Claude。外部资料只读了 README、摘要和检索结果，没有读全文；标“未核实”的需要读原文再引用。

## 一句话结论

两件事都可行，而且应该**绑在一起做**：用果蝇方向的“已知真值玩具问题”当第一个真实负载，只为它搭 AgentConsole 需要的最小几块（任务目录、结论账本、人工检查点、微信提醒）。这样既不会空搭平台，也能直接解决“overnight 研究看不懂”。“哪种多 agent 分工有效”可以作为 PRTS 的研究题，但单问“分出 planner/executor/reviewer 有没有用”已经很拥挤，要换一个角度（见 §3）。

## 1. 任务 A：AgentConsole 从“观察”走向“协作 + 干预”

### 现状与差距

| 你要的能力 | 现在有什么 | 缺什么 |
|---|---|---|
| 看见 agent 在干什么 | AgentConsole：会话树、状态、recap、事件循环（只读，不调 LLM） | — |
| 分工、传递结果 | `ops/dispatch.sh` + `registry.jsonl`；拖动合并（手动打包上下文） | “任务”这个对象本身：谁领了什么、产出放哪、下一步给谁 |
| 失败反馈 | 派发脚本能发现“启动即死”；夜间 supervisor 按轮跑 | 失败要回流给上游（改执行 / 改计划 / 重来），现在靠 Claude 人工看日志 |
| 人工提醒 | CodexBridge 微信（日报、刚上线的自动建提醒） | 由 agent 事件触发的提醒 |
| 人工干预 | 只能进会话里打字 | 停止、改目标、提反例、要求复现这些“结构化”的干预 |

### 参考项目能借什么

- **QED**（[proofQED/QED](https://github.com/proofQED/QED)）：数学证明流水线。值得借的是它的**文件协议**，不是数学部分：
  - 计划写成 `decomposition.yaml`（中间结论组成的 DAG）；
  - 核查分两层：结构核查、逐步核查；
  - 失败分三级升级：改证明 → 改计划 → 重写，每级有次数上限；全部用完时写 `failure_analysis.md`；
  - 人可以在运行中往 `human_help/` 里写提示和硬性规则；
  - 产出目录 `attempt_N/revision_N/` 直接对应重试层级，人能顺着找。
  - 这和 PRTS 的“文件 + git、单一写者”思路完全一致，可以几乎原样采用。注意它默认跳过所有权限确认运行，我们不照抄这一点。
- **LibreChat**（[LibreChat-AI/LibreChat](https://github.com/LibreChat-AI/LibreChat)）：本质是多模型聊天前端，带子 agent、MCP、权限的 Ask/Allow/Deny 和 Trace Viewer。**不建议往这个方向做**：它以聊天为中心，而你要的恰好不是聊天。可借的只有一点：按时间展开一次运行里的模型调用、工具调用和花费（Trace Viewer）。

### GPT 建议 2（Research Dashboard）的评价

方向对，而且有人在做同一件事（未核实，需读原文）：
- [AI Scientist Mission Control](https://arxiv.org/pdf/2608.28637)：用可视化把人有限的注意力引到最值得看的产出；
- [Claim-aware Observability](https://arxiv.org/pdf/2608.18312)：认为提示词和工具调用日志不够，应把“结论 → 证据”的链接和人工干预本身当作一等审计记录。

这说明想法是对的，也说明不能只做“又一个 dashboard”。

GPT 列的五个操作，每个都要落到一个文件动作上，才实现得了：

| 操作 | 落到文件上 | 谁来执行 |
|---|---|---|
| 打开原始证据 | 每条结论都链接到 `evidence/` 下的具体文件和生成命令 | Console 直接打开 |
| 要求复现 | 往任务队列写一条“用给定命令重跑并比对数字” | dispatch 派给一个新 Codex（不复用原 agent 的上下文） |
| 提反例 | 往 `human/` 写反例，reviewer 下一轮必须回应 | reviewer agent |
| 调整下一阶段目标 | 改 `goal.md`；agent 每轮开始时现读 | planner |
| 在 checkpoint 停止 | 写 `STOP` 文件；supervisor 每轮之间检查 | 确定性脚本，不靠 LLM 自觉 |

### 可行性

- **技术难度**：中等。每一块都是已有组件的小扩展，不需要新框架：AgentConsole 读一个新目录格式，dispatch 增加一种任务类型，supervisor 检查 STOP 文件，CodexBridge 推送事件。
- **工作量**：最小版本约 1–2 周业余时间，代码交给 Codex 写。
- **最大风险**：没有真实负载就搭平台，最后做出一个没人用的界面。所以先做任务 B，A 只做 B 用得到的部分。

## 2. 任务 B：果蝇（线虫试点）当 autoresearch 试验场

### 先纠正一个前提

GPT 建议 1 说“构造一个 5 节点模拟网络，事先知道真实连接，再尝试重建”。这件事**你已经在 300 个节点上做过了**：`DigitalFly/MyWork/worm_effectome` 的 Exp1，就是线虫连接组上的已知真值模拟，已经得出“刺激覆盖是瓶颈”等结论。Exp2 也已经拟合了真实的 Randi 图谱。

5 节点版本仍然值得做，但理由变了：**不是为了验证方法，而是为了给 autoresearch 一个人能逐项核对的考场。**
- 5×5 的矩阵一眼看得完，每条结论都能手算核对；
- 线性系统的可辨识性有解析结论（哪些边在部分刺激、部分观测下能被确定），可以作为标准答案；
- 一次运行只要几秒，一晚上能跑完几百轮。

### 为什么 overnight research 会看不懂

回看 10-20 那次夜间实验，看不懂的原因有四个：
1. **没有标准答案**：agent 报告“找到了 X”，你没法快速判断真假，只能读它的推理；
2. **产出是叙事，不是结论**：几千字的报告，而不是“一句话结论 + 一个数字 + 一个文件 + 一条复现命令”；
3. **检查点之间步子太大**：一晚上十几轮，中间没有你能介入的点；
4. **agent 可以自己改评价标准**：改数据、改指标、换问题，事后很难追。

### 对应的设计

- **真值阶梯**，逐级放开，每级都有标准答案或强基线：
  1. 5 节点，全观测、全刺激 → 解析可辨识，答案唯一；
  2. 5 节点加一个隐藏节点或部分刺激 → 有解析结论“哪些边辨识不了”；
  3. 20–50 节点随机网络；
  4. 300 节点线虫（= 现有 Exp1，已有人工结论可对照）；
  5. 真实 Randi 图谱（= 现有 Exp2，噪声上限 0.68 是硬天花板）。

  agent 在第 1–4 级的发现都能自动判对错；只有第 5 级需要人判断。
- **结论账本**（claims ledger）：每条结论只能是一句话 + 数字 + 证据文件 + 复现命令。不在账本里的内容不算结论。
- **冻结评价**：数据、真值和评分脚本放在 agent 只读的位置。
- **短轮次 + 硬检查点**：例如每 N 轮或每次声称有新发现时停下，生成一页摘要推到微信。你只读摘要，想深究再从 dashboard 点进证据。
- **第一个真问题**：Exp3“主动选择下一批刺激对象”很适合交给 autoresearch。目标明确（让模型的不确定性下降最快），模拟很便宜（CPU 上秒级），在真值阶梯上能自动打分。

### 可行性

- **5 节点考场和真值阶梯**：高，几天就能搭好，计算几乎免费。
- **autoresearch 跑 Exp3**：中高。风险是 agent 只“重新发现”教科书结论；但在考场阶段这正是想要的及格线。
- **注意**：DigitalFly 不是 git 仓库。要让 agent 自动跑并且可以回滚，先 `git init`，至少把 `MyWork/worm_effectome` 管起来。

## 3. 研究题：什么样的多 agent 合作是有效的

### 已有工作（不完整，需 Codex 系统调研）

- **按角色分工的框架很多**：MetaGPT、ChatDev（按软件公司的岗位分工）、AutoGen、Magentic-One（一个编排者，加上任务账本和进度账本）、Google AI co-scientist（生成 / 反思 / 排名 / 进化），以及 QED。
- **planner / executor / verifier 本身**：2026 年的 [VeriMAP](https://arxiv.org/html/2510.17109v1)（EACL 2026）有 planner、executor、verifier 和 coordinator，报告比单 agent 基线好，但在难题上只高出几个百分点。[PEAR](https://preview.aclanthology.org/ingest-eacl/2026.findings-eacl.237.pdf) 发现 planner 弱比 executor 弱伤害更大。
- **反面证据**：失败分类研究（Cemri 等 2025，“Why Do Multi-Agent LLM Systems Fail?”）、Google 2025 年关于 agent 系统扩展的研究，以及 Cognition 的“Don't build multi-agents”都指出：很多场景下多 agent 不比单 agent 好，协调本身就是新的失败来源。以上是我凭记忆列的，引用前要核实。

**判断**：单问“分出 planner/executor/reviewer 有没有用”，已经有不少人做，结论也是“看情况、提升有限”。

### 建议的 PRTS 角度

把指标从“任务成功率”换成**“人要花多少核查精力，才能信任一条结论”**。这正是你遇到的痛点，也和 PRTS“人机协作”的定位一致。
- **自变量**：合作结构。单 agent；planner + executor；planner + executor + reviewer；再加“独立复现者”。
- **因变量**：每条被人接受的结论的真伪（真值阶梯上可以自动判）、人读了多少字、点开了几次证据、多少错误结论被 reviewer 拦下或漏掉。
- **试验场**：就是 §2 的真值阶梯。前 4 级有标准答案，所以能客观地给每种结构打分，这是大多数多 agent 论文没有的条件。

这让任务 A、B 和研究题合成一件事：B 提供有真值的考场，A 提供执行和干预的骨架，研究题比较不同骨架。

## 5. 补充（同日，用户反馈后）

- **已定**：借 QED，不用 LibreChat。每个研究方向一个专用 session，另设研究统筹 session；写权限按目录划分，规则写在 `research/PRTS/AGENTS.md`。
- **总纲**：人的精力有限，而 agent 的产出速度已超过人能处理的速度。本报告的研究题（E5）是总纲的一部分，评价标准另行讨论。
- **果蝇不算 autoresearch**：果蝇现在是按步骤管控的研究。用户理想中的 autoresearch 是：给一个 benchmark，让 AI 一直干到超过为止，人尽量不管。aquant 涉及真钱，暂时不适合这样做。

### 胡瑞方向能否做 autoresearch

**他的方向**（据 10.15 汇报）：用视觉和嗅觉生成参考路径（ref），交给质文的 VNC 执行，让果蝇自主找到食物。
- **他的近期工作基本是手工调参**：轨迹约束（最小转弯半径 7 mm、速度 + 曲率）、ref buffer 长度（1000–5000 步）、朝向损失、指数型停滞惩罚。
- **现在的问题**：轨迹接近椭圆，训练数据只有几十条。

**适合程度：高。** 这正是"固定评测、让 agent 反复改训练配置"这类 autoresearch 擅长的形状：
- **指标天然存在**：固定场景和随机种子下，到达食物的成功率和用时，可以自动打分；
- **失败便宜**：不涉及真钱，坏了重来；
- **搜索空间清楚**：约束、奖励项、buffer 长度、数据量。

**前提和风险：**
1. **他的代码、检查点和同意。** 这是他的项目，要先征得他同意并拿到代码；用组里的算力还要问清楚。
2. **一轮的耗时决定可行性。** 如果训练一次要几小时，一晚上只能跑几轮，那 autoresearch 的优势有限。要先测一轮多久，算一下一晚能跑多少轮。
3. **评测必须冻结。** 场景、种子、评分脚本对 agent 只读，否则它会去改评测本身，或者钻仿真的空子，比如让果蝇在原地抖动刷分。
4. **能替代的只有他计划的第 1 步。** 第 2 步（从 DN 神经元学会身体状态）和第 3 步（加入起飞和降落）是研究问题，没有现成的 benchmark。

**关于"让他放弃当前计划"：**
- **能做到的**：用实验给出证据。若 autoresearch 在同样预算下明显超过他手调的结果，可以说明"手调这条路效率低"。
- **做不到的**：证明"这个方向走不通"。agent 没找到更好的配置，只说明在给定预算内没找到。
- **建议的说法**：把结果作为对照提供给他，而不是作为让他放弃的理由。

**建议的最小步骤：**
1. 和胡瑞确认意愿，拿到代码。
2. 测一轮训练加评测的耗时。
3. 把评测脚本冻结。
4. 先跑单 agent 基线一晚，看摘要能不能读懂。
